# `.oxlintrc.json` — pourquoi ce ratchet

`oxlint` tourne en gate bloquante (`npm run lint:fast`, appelé par `npm run check`).
Le schéma de config est strict et n'accepte aucune clé de commentaire : la
justification vit donc ici.

## `categories.correctness: "error"` — bloquant

C'est l'étage qui attrape de vrais bugs. Il est vert aujourd'hui et doit le rester.

## Les règles en `warn` — baseline qui ne peut que décroître

Au 26/07/2026, `oxlint src` remontait **111 avertissements** de **style**, pas de
correction : `no-array-sort` (45), `no-underscore-dangle` (23), `no-array-reverse`
(11), `prefer-string-starts-ends-with` (10), etc.

Les passer bloquantes d'un seul coup aurait cassé la gate sans corriger un seul
bug — et la seule façon de la refaire passer vite aurait été de désactiver les
règles, c'est-à-dire de tricher la gate. Elles restent donc **visibles** (chaque
`npm run lint:fast` les affiche) et se résorbent au fil des passes.

**Règle du ratchet : la baseline ne peut que décroître.** Dès qu'une règle tombe
à zéro occurrence, retire sa ligne de `rules` — elle repasse bloquante via
`categories`. N'ajoute jamais une règle ici pour faire taire un nouveau warning :
corrige le code.

## `unicorn/no-invalid-fetch-options: "off"` — faux positif vérifié

Deux sites signalés (`postgrest.ts:91`, `github.ts:245`) passent
`body: body !== undefined ? JSON.stringify(body) : undefined`. En `GET`, `body`
vaut donc `undefined` et le fetch est valide : la règle ne sait pas lire le
ternaire. Vérifié à la lecture du code, pas supposé.
